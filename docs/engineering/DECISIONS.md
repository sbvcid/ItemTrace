# ItemTrace Engineering Decisions

重要工程決策與其背景、選項、決定、取捨記錄。

---

## D1. AI Provider 與 ItemTrace AI Contract 的分離

### 背景
ItemTrace 的 AI 能力依賴外部 Vision 模型（Google Gemini / OpenRouter / Custom），但系統不應被特定廠商綁定。需要清晰的介面合約，使 AI 廠商可替換、可離線、可未來升級。

### 選項
1. **直接依賴 OpenAI API** —— 簡單，但被 OpenAI 綁定
2. **建立 ItemTrace AI Contract** —— 抽象層次高，廠商可替換 ✓
3. **自訂模型微調** —— 維護成本高，短期不可行

### 決定
**採用 Option 2：ItemTrace AI Contract**
- `shop/ai_client.py` 定義統一呼叫介面
- 支援 OpenAI / Gemini / OpenRouter / Custom 端點
- Suggestions 結構化標準：`[{"field": "...", "value": "...", "confidence": ..., "source_photo_index": ...}]`
- 配置存在 `tools/ai_config.local.json`（不版本控制，安全隔離密鑰）

### 取捨
- **優勢**：廠商無鎖定，使用者可選擇成本/品質平衡
- **成本**：需維護多個廠商的 API 轉接層
- **風險**：各廠商 API 變更時需更新適配

### 驗證方式
- `tests/test_ai_provider_errors.py` 驗證錯誤處理
- `tests/test_ai_config.py` 驗證配置切換
- 新增廠商時補充適配測試

**狀態**：✓ Accepted（已實作於 shop/ai_client.py）

## D2. 新欄位、動態屬性與使用者備註的儲存策略

### 背景
ItemTrace 既要捕捉 AI 自動填入的結構化欄位（品名、型號、序號），也要支援使用者的自由備註（「換了副廠線材」「防潮箱 C-02」）。簡單的單一文本欄位無法支援兩者的獨立維護與搜尋。

### 選項
1. **統一文本欄位** —— 簡單但無法區分 AI vs 人工，搜尋低效
2. **拆成多個固定欄位** —— AI 資料集中，使用者備註分散，難以擴展
3. **JSON 動態屬性 + 固定欄位** —— 結構清晰，易於擴展 ✓

### 決定
**採用 Option 3：JSON 動態屬性 + 固定欄位分離**
- **固定欄位**（AI 與 user 都可寫，但語意明確）：
  - `items.name`、`brand`、`model`、`category`、`condition` —— 由 AI 初始填充，user 可編輯
  - 搜尋索引涵蓋這些欄位
  
- **JSON 屬性** (`items.attributes` JSON 物件）：
  - `purchase_date`、`warranty_until`、`location`、`notes`
  - 動態擴展空間，使用者自由維護
  - 搜尋時可選索引

- **區分來源**：
  - Suggestions 表記錄 AI 提案源頭
  - Events 表記錄人工修改
  - UI 清楚標示「✨ AI 建議」vs「📝 你的備忘」

### 取捨
- **優勢**：結構 + 自由度平衡，易於搜尋與擴展
- **成本**：需設計清晰的欄位歸類與 UI 標示
- **風險**：重複邏輯（某欄位同時出現在 fixed + attributes）需嚴格約束

### 遷移策略
- `items.attributes` 已存在於初始 schema（`TEXT NOT NULL DEFAULT '{}'`，`shop/schema.sql`），無需遷移
- 既有資料無 attributes 時視作 `{}`
- 不強制遷移已有數據

### 驗證方式
- 屬性契約測試：`attribute:<key>` pattern 驗證、單鍵合併、不覆蓋使用者資料、事件快照（Phase 2B，`tests/test_repo_suggestions.py` 等）
- 搜尋測試：accepted 建議值可被檢索

**狀態**：✓ Accepted 且已實作（`items.attributes` 於初始 schema 落地；Phase 2B 加入 `attribute:<key>` AI 提案契約、單鍵合併與 accepted 值搜尋）

## D3. SQLite 全文索引與中文搜尋策略

### 背景
ItemTrace 需要支援毫秒級搜尋（< 50ms for 1000+ 紀錄），部分字串匹配（型號「4070」→「RTX4070」），以及繁簡體互搜。SQLite FTS5 是輕量方案，但中文分詞與繁簡需特殊處理。

### 選項
1. **無全文索引，逐行 LIKE 查詢** —— 簡單但 O(n) 低效，超過 100 紀錄即無法接受
2. **SQLite FTS5 + 簡單中文分詞** —— 輕量，需手動處理繁簡 ✓
3. **遷移至 Elasticsearch / Meilisearch** —— 功能完善，但引入外部依賴，違反 local-first 原則
4. **自訂 Porter Stemmer for Chinese** —— 維護成本高

### 決定
**已實作：SQL `LIKE` 搜尋（v1 即定案並落地）**
- `shop/repo.py`：品名、品牌、型號、分類、備註、attributes 字串比對＋identifiers 正規化比對＋accepted 建議值命中
- 不用 FTS5 的實測依據（SPEC-v1 §7.2）：`trigram` tokenizer 要求查詢該 ≥ 3 字元（兩字中文 0 命中）；`unicode61` 不切中文（整詞才命中）。目前資料量（數千筆內）LIKE 全表掃描足夠

**FTS5 索引：未採納、未排程**
- 保留為未來候選：若資料量成長到 LIKE 全表掃描不足，再評估 FTS5 `trigram`＋短查詢退回 LIKE 的混合方案（屆時需重做兩字中文實測）

### 取捨
- **優勢**：零外部依賴，符合 local-first；兩字中文與半截序號當前皆可靠命中
- **成本**：資料量大幅成長後效能會下降（屆時再評估）
- **風險**：無（現行規模下 LIKE 語意正確）

### 索引維護
- 現行無獨立搜尋索引表，無維護需求
- 若未來採用 FTS5：觸發器增量更新＋重建／最佳化維護端點（`POST /api/admin/search-index/rebuild`／`optimize`）

### 驗證方式
- 搜尋行為測試（現行）：兩字中文、半截序號、accepted 建議值命中
- 效能基線：Phase 5 候選啟動時評估

**狀態**：部分採納——LIKE 搜尋已實作；FTS5 索引**未採納**（歷史提案保留，未排程）

## D4. 繁簡轉換與原始資料不改寫原則

### 背景
支援繁簡互搜時，需要決定：搜尋時即時轉換 vs 預先轉換存儲？後者違反「原始資料神聖」原則，前者的效能取決於轉換演算法。

### 選項
1. **存儲時轉換備份** —— 違反原始資料原則，資料表膨脹
2. **搜尋時轉換** —— 保持原始資料完整，效能依轉換庫 ✓
3. **建立轉換索引表** —— 折衷方案，需維護同步

### 決定
**採用 Option 2：搜尋時動態轉換**
- 所有用戶輸入資料（品名、備忘等）**原樣保存**，不轉換
- 搜尋時：用戶輸入 → 繁簡轉換 → 查詢 FTS5 （同時查詢原詞）
- 轉換庫選擇：OpenCC（C++) 或 python-opencc（有 Python 綁定）

### 取捨
- **優勢**：原始資料完整，日後支援其他轉換（簡 → 繁 → 粵語 等）無需重構資料
- **成本**：每次搜尋需轉換，增加 CPU 負擔（但通常 < 1ms）
- **風險**：轉換庫失效 / 更新時搜尋結果可能變化

### 驗證方式
- 搜尋轉換性能測試：單次轉換耗時 < 1ms
- 資料驗證：隨機抽查 100 筆紀錄，確認原始資料未被修改

**狀態**：未採納（未實作）——現行無繁簡轉換；保留為 Phase 5 搜尋強化啟動時的設計參考（屆時需重新評估轉換庫與效能）

## D5. 垃圾桶與永久刪除的資料生命週期

### 背景
刪除紀錄涉及資料安全與使用者體驗。需要平衡：使用者意外刪除的後悔機制 vs 確保資料最終清理。

### 選項
1. **立即永久刪除** —— 簡單但無法恢復，風險高
2. **軟刪除 (deleted_at 標記) + 30 天保留** —— 標準做法，給使用者反悔空間 ✓
3. **無限期保留** —— 安全但垃圾堆積
4. **加密而非刪除** —— 複雜，維護成本高

### 決定（已實作：Phase 3，2026-10-11）
**採用既有 `status='void'` 的垃圾桶模型；不引入 `deleted_at`、30 天保留或背景清除**：

- **移至垃圾桶**：`status='void'`（零 migration），預設列表排除，垃圾桶頁可見
- **還原**：`POST /api/items/{id}/restore`，移入前狀態由事件歷史推導（不可靠時安全預設 active）
- **永久刪除**：`DELETE /api/items/{id}`，僅限垃圾桶紀錄、由使用者明確執行；單一交易清除 DB 紀錄與全部相關 events；照片目錄先可逆改名 `.purge/` 再移除
- **不做自動過期清除**：無排程 job；備份快照不受永久刪除觸及

### 未採納的早期提案（歷史紀錄）
早期曾規劃「`items.deleted_at` 軟刪除＋30 天保留＋背景 cleanup job 自動永久刪除」（Option 2 原案）。**未採用**：在垃圾桶與還原行為經實際使用確認前，不可逆的排程自動刪除資料風險過高；且 `void` 狀態機已存在，零 migration 即滿足需求。未來若要自動過期，需先定案資料安全政策並明示使用者。

### 資料安全驗證清單（已實作的防線）
1. 資料庫紀錄刪除（單一交易，含全部相關 events 與 json payload 補掃；外鍵 RESTRICT 為最後防線）
2. 照片檔案移除（`files/<item_id>/` 整棵樹；提交前先可逆改名 `.purge/`）
3. 失敗可診斷（刪檔失敗回 500＋完整路徑；鎖檔時中止且 DB 零變更）
4. 編號不回收（`schema_meta.items_seq`，零 DDL）
5. 路徑守衛（照片路徑不在 `files/<id>/` 底下時拒絕刪除）

### 取捨
- **優勢**：使用者有完整的反悔空間（還原至移入前狀態）；資料刪除完全由使用者掌控，無自動不可逆風險
- **成本**：垃圾桶長期不清理會佔空間——由使用者自行決定何時永久刪除
- **風險**：無自動清理意味依賴使用者手動管理（刻意取捨）

### 驗證方式
- Phase 3 測試 repo×13＋API×6＋V3×2（位於 `tests/test_repo_items.py`、`tests/test_api.py`、`tests/test_v3_core_slice.py`）：預設排除、還原原狀態／預設值／事件、purge 全清、路徑守衛、鎖檔零副作用、刪檔失敗回報、編號不回收
- 驗證永久刪除：查詢資料庫、檔案系統確認完全無跡（見 AGENT_GUIDE §6）

**狀態**：✓ Accepted 且已實作（Phase 3；30 天自動清除未採納）

## D6. 原始照片、衍生預覽、備份的邊界

### 背景
ItemTrace 強調原始紀錄不可破壞，但同時需要快速預覽與備份。需要定義哪些檔案必保留、哪些可重生。

### 檔案分類
1. **原始照片** (`files/{item_id}/original/`) —— 神聖，永不覆寫、永不壓縮
2. **衍生預覽** (`files/{item_id}/derived/`) —— 可重生，用於 UI 快速顯示
3. **備份** (`backups/shop-{timestamp}/`) —— 完整快照，用於災難恢復

### 決定
- **原始照片**：byte-for-byte 保存上傳檔案，不修改、不轉檔、不重新壓縮
  - 即使是 HEIC / WebP 等「非標準」格式，也原樣保留
  - 用戶下載時提供原檔

- **衍生預覽**：
  - 縮圖 1024×768 JPEG 用於首頁卡片
  - 大圖 2048×1536 JPEG 用於詳細頁
  - 可刪除重生，不影響原始資料
  
- **備份**：
  - `python shopctl.py backup` 使用 SQLite `Connection.backup()` + `shutil.copytree`
  - 保留最近 30 份快照（滾動保留）
  - 備份內容完全自足，整個資料夾複製回去即還原

### 取捨
- **優勢**：原始資料與使用者體驗完全解耦
- **成本**：磁碟空間（衍生預覽 + 多份備份）
- **風險**：衍生預覽與原始不同步時使用者看不到新照片

### 驗證方式
- Phase 1+ 測試：上傳各種格式相片，下載後驗證 byte-for-byte 相同
- 備份還原測試：備份 → 刪除 → 還原 → 驗證資料完整

**狀態**：✓ Accepted（已實作原始照片保護）

## D7. 未來 Windows 封裝和使用者資料位置

### 背景
ItemTrace 當前是命令行啟動的純 Web 應用。未來封裝為 Windows Store 應用或 EXE 時，需要決定：資料存放位置、安裝路徑、更新機制。

### 選項
1. **固定位置** （例 `C:\ItemTrace`）—— 簡單但不尊重使用者偏好
2. **%APPDATA% 位置** —— 標準 Windows 做法 ✓
3. **使用者自選位置** —— 尊重使用者但複雜度高

### 決定
**採用 Option 2：%APPDATA% 位置（Phase 7 決定最終細節）**
- 資料默認位置：`%APPDATA%\ItemTrace\` （例 `C:\Users\username\AppData\Roaming\ItemTrace\`）
- 可選：提供「選擇位置」嚮導，讓使用者指定 USB 隨身碟或網路驅動器
- 當前本地開發：仍使用 `config.json` 指定 `data_root`

### 取捨
- **優勢**：符合 Windows 使用者期望，支援多使用者
- **成本**：需調整 path 解析邏輯，測試多個路徑場景
- **風險**：某些網路驅動器可能不支援 WAL 模式

### 驗證方式
- Phase 7 測試：在 %APPDATA% 位置啟動、建檔、搜尋，驗證功能完整

**狀態**：Proposed（Phase 7 實作時最終確定）

## D8. AI 自動更新的邊界與復原安全（Phase 2C-B/C/D）

### 背景
AI 會隨新證據自動更新判讀（描述、屬性、身分修訂）。若處理不當，自動更新可能覆蓋使用者意圖、隱藏矛盾證據，或讓「復原」反過來破壞後續編輯。2C-C 的 Live 實測即抓到「過期 undo 覆寫後續編輯」缺陷。

### 決定
1. **自動套用分層**（2C-B）：描述性 `attribute:*` 自動、空身分自動、先前由系統自動填入的身分可自動修訂；`identifier:*`／category／condition／notes 永遠人工確認；購買資訊僅在「同一張照片同時提供身分資訊」時自動，否則升級衝突。
2. **撤銷安全**（2C-D）：undo 只在「現值＝該次自動套用的值」且「套用後沒有任何改到同一欄位的事件（值改掉又改回亦算）」時執行；不符回 409、**零副作用**。批次逐欄位獨立，UI 逐項列出「未復原」欄位。
3. **判讀提示**（2C-D）：看得見但認不出身分時，用描述性 `name`＋`attribute:description`（先寫看見的，推測用「看起來像」）；不同照片支持不同身分時分別輸出（多值），由系統的重複值偵測升級衝突，不默默擇一。
4. 以上全部**不依賴模型自報信心**（2C-A 實測：0.90~1.00 無鑑別力）。

### 取捨
- 優勢：可回復、可稽核、保護使用者意圖；契約與政策皆可離線回歸（recorded replay）。
- 成本：模型在「有上下文＋兩張身分標籤」時仍可能擇一（R 型）；目前由 auto 修訂 banner＋可復原承擔風險。
- 風險：prompt 無法保證模型遵守分列規則 → 以評測（C6）與政策側重複值偵測兜底；不採品牌特例規則。

### 驗證方式
- `tests/test_ai_analyze.py`（過期 undo×6、跨照片衝突×2）、`tests/test_v3_core_slice.py`（靜態接線）。
- `tools/evaluate_models.py --offline`（10 情境契約回歸）；`tools/validate_autonomy_live.py`（Live 行程，僅合成圖）。

**狀態**：✓ Accepted（2C-B/C/D 實作與驗證；R 型限制記錄於 AI-AUTONOMY-VALIDATION.md）

## D9. SR-1 安全基線（Host／Origin／標頭、key 外送、綁定、媒體輸出）（2026-10-10）

### 背景
Security Audit 1 確認（隔離實測）：F1 DNS rebinding（無 Host/Origin 驗證，loopback 綁定亦可被任意網頁全控）、F2 已存 API key 可被轉送到呼叫者指定的 base_url、F3 無 body 端點可 CSRF、F5 實值綁 0.0.0.0、F6 儲存型 XSS 與媒體主動內容原樣供檔。

### 決定
1. **路由前守門**：Host ∈ 白名單（loopback 全形式＋`server_host`＋config `allowed_hosts`）；有 Origin 時必須同源（host∈白名單、埠一致、`null` 拒絕）。
2. **變更類自訂標頭**：POST／PATCH／PUT／DELETE 一律要求 `X-Requested-With: ItemTrace`（瀏覽器跨站帶不了自訂標頭；前端與工具統一附加）。缺少 Origin **不**單獨構成信任。
3. **key 外送邊界**：`/api/settings/ai/test` 的已存 key 只送往已知 provider preset；自訂 base URL 必須由該次請求帶臨時 key。
4. **綁定 opt-in**：預設 loopback；非 loopback 需 config `"allow_lan": true`（未設定拒啟）。信任區網模型文件化，且明示**不能取代認證**。
5. **輸出安全**：前端 `escapeHtml` 全面套用；回應 `nosniff`／`Referrer-Policy`／HTML CSP（`script-src 'self'`、`frame-ancestors 'none'`）；`/files` 非圖片 → `attachment`/`octet-stream`＋`default-src 'none'; sandbox`；禁 inline 事件處理器。

### 取捨
- 手動 curl／腳本需多帶一個標頭；自訂 provider 測試需當次貼臨時 key——換得「瀏覽器不可被跨站利用」與「長期 key 不外流」。
- 不引入登入系統（維持 local-first 單人）；F4（資源上限）、F7/F8（縱深）保留後續。

### 驗證

## D10. SR-2 資源上限、輸出衛生與列印管線硬化（2026-10-10）

### 背景
Security Audit 1 的 F4（資源上限）、F7（資訊衛生）、F8（列印管線）在 SR-2
逐一重驗後實作。F8 重驗時發現兩個**可實際執行 JS** 的 mXSS（見
SECURITY-AUDIT.md「SR-2」節）：立即結束註解（`<!-->`）與實體編碼標記
（`&lt;img …&gt;`）都能穿過存檔驗證、由 renderer 原樣重送進列印瀏覽器。

### 決定
1. **資源上限是明示的 config 欄位**（`shop/limits.py` 為單一事實來源）：
   body 32 MiB、單檔 24 MiB、每請求 20 檔、圖片 50 MP、列印光柵 60 MP、
   AI 每分鐘 10 次、Template 1 MB。超限回 413／400／429；**先前已成功
   的檔案保留**，不因後段失敗回滾。上傳端**不設型別白名單**（D6：證據
   原檔不可被拒收），安全處理放在輸出端（SR-1 附件化／CSP、SR-2
   inline MIME 白名單、像素上限）。
2. **body 上限用純 ASGI middleware**：有 Content-Length 直接拒；chunked
   逐塊累計，超限由 middleware 自己送 413（FastAPI 會把 body 讀取例外
   吞成 400，所以不能只丟例外）。
3. **像素防護零解碼優先**：JPEG（SOF）／PNG（IHDR）在上傳時讀檔頭判寬高；
   Pillow 只在 analyze 縮圖時作為其他格式的兜底。
4. **AI 節流是單行程滑動視窗**（不引入 Redis 等外部服務）；限制誠實
   文件化：多 worker 時為 N 倍、重啟歸零。
5. **列印輸出採「重新序列化」策略**：renderer 不再原樣轉貼模板——
   註解丟棄、文字 escape（`<style>` raw text 除外）、屬性 allowlist、
   render 前再驗一次。validator 同步加嚴（註解含 `<`／`>` 拒絕）。
6. **列印瀏覽器預設保留 sandbox**：實測本機新版 headless 不需
   `--no-sandbox`；受限環境用 `ITEMTRACE_PRINT_NO_SANDBOX=1` 明示退回。
   實測 `--blink-settings=scriptEnabled=false` 會讓 `--print-to-pdf` 失效，
   不採用；JS 的防線在 renderer 端（輸出不可能含可執行內容）。
7. **API 文件預設關閉**（`enable_docs` 開發選項）；API `no-store`、
   照片 `private`、靜態資產維持可快取；`ConfigError` 對外通用化、細節
   只進伺服器 console。

### 取捨
- 手動 curl／自訂工具在多檔上傳時會拿到 413／400 而非默默接受；換得
  「小檔大像素」與巨量 body 不會打爆記憶體。
- 模板作者若在註解裡用 `<`／`>`（例如 `<!-- a > b -->`）存檔會被拒——
  訊息明確，且此類註解在列印情境沒有功能價值。
- 節流不是分散式；以本專案「local-first、單一桌面實例」的定位，這是
  刻意取捨（文件已載明多 worker 的語義）。
- 列印 JS 引擎仍開著；我們選擇「不讓可執行內容抵達瀏覽器」而不是
  「關 JS」（後者在目前 Chromium 沒有可靠的 CLI 開關，實測會壞）。

  去路徑化、註解／實體 mXSS、render-time 驗證、sandbox 命令契約、

## D12. 既有紀錄 AI 重新分析的完整上下文建構與新證據自動套用決策（2026-10-11）

### 背景
既有紀錄追加照片或重新分析時，過去僅傳入當前部分欄位與首尾照片切片，缺乏修改歷程、已登記識別碼與歷次建議結果（已接受／已拒絕／被取代）。模型無法得知舊值如何形成、使用者曾修正過什麼；同時後端自動套用政策（`_auto_decision`）曾採「欄位只要曾被人工編輯過就一律擋下」的機械式規則，導致即便使用者事後補拍了清晰清晰的銘牌或包裝盒新照片，AI 也無法自動更新正確的品牌或型號。

### 選項
1. **僅修改提示詞** —— 模型知道歷史但後端自動套用仍機械式阻擋，無法改善實際產品更新體驗。
2. **新增專用資料表記錄歷史與狀態** —— 破壞輕量 local-first 架構與現有資料庫結構，引發 migration 風險。
3. **善用既有事件與建議表，擴展上下文與細緻化自動套用政策** —— 零資料庫 schema 變更，完整提取歷史脈絡，並以時間軸嚴格判定新證據。✓

### 決定
**採用 Option 3：以既有資料模型建構完整上下文與時間軸驅動的自動套用**
1. **完整單筆紀錄分析上下文（`build_analysis_context`）**：
   - 核心 API 與外部 adapter（`tools/analyze_item.py`）共用同一套上下文組裝與照片選取函式。
   - 包含【目前紀錄狀態】（固定欄位＋動態屬性與備註）。
   - 包含【已登記識別碼】（類型、值、來源照片追溯）。
   - 包含【本次分析照片與觀測】（時序標註 `[初始建檔照片]`、`[後續追加照片]`、`[含識別碼證據]`）。
   - 包含【重要歷史修改】（由 events 提取人工修改欄位與時間、系統自動套用與撤銷 Undo 紀錄）。
   - 包含【歷次 AI 判讀與結果】：**精確區分語意**——系統自動套用標示為「⚙️ 系統先前自動套用」；使用者手動接受標示為「✓ 使用者已採納」；使用者 Undo 標示為「↩️ 使用者先前撤回（Undo）」；使用者明確拒絕標示為「⚠️ 使用者明確拒絕」。曾被撤回或拒絕的值標註「無新證據時請勿重複提議；此值永遠不會自動套用」——拒絕只禁止靜默自動套用，不禁止在新證據支持下再次提出（屆時仍僅為待確認建議）。
   - **取用順序與上限**：歷次建議按時間排序後取**最近**的各類配額（拒絕 8／已採納 8／已取代 4），不因正序排序而保留最早紀錄；讀取窗口同樣以最新紀錄優先（`list_suggestions(..., newest_first=True)`，欄位來源追蹤同步採用），建議總數超過取用上限時仍能涵蓋最新的拒絕／撤回。
   - 注入結構化重新理解指引：平衡新證據與歷史修正；證據不足時保留現狀。
   - **外部工具邊界**：外部 adapter 受限於最小權限設計不讀取內部 events，上下文明確標記限制「無手動修改記錄或未取得歷史」，不宣稱完全同步。
2. **關鍵照片保留與精準來源映射（`select_photos_for_analysis`）**：
   - 預設上限 8 張（`MAX_PHOTOS = 8`）；回傳張數保證不超過 `max_photos`（2／3 等小預算亦同——初始保留隨預算縮放，修正曾超出請求張數的缺陷）。
   - **必須保留**：Photo 0（初始建檔基線）與最新追加照片（預算允許時保留最新 2 張；預算只有 2 張時保留最新 1 張）。
   - **優先保留**：包含已登記識別碼的照片。8 張預算下提供最多 5 個名額給識別碼照片；$\le 5$ 張時全數保留，$> 5$ 張時保留最新 5 張；小預算（2~3 張）時基線與最新證據用盡預算，識別碼無名額。
   - **餘額分配**：由最新照片往前依序補齊；無識別碼時維持「最早 2 張＋最新 N-2 張」。
   - 保持嚴格時序排序，確保 AI 建議的 `source_photo_index` 精準對應至選取切片中的 `source_photo_id`。
3. **細緻化欄位溯源與證據／輔助信心門檻自動套用規則（`_auto_decision` / `_field_provenance_details`）**：
   - 新增 `FieldProvenance` 結構，精準記錄最後人工修改時間點與歷史拒絕/復原值清單。
   - **真正新證據判定**：比對照片拍攝時間與 ULID 事件順序，只有在使用者修改**之後**拍攝/上傳的照片才算新證據。
   - **輔助信心門檻（`confidence >= 0.90`）**：新照片不得僅因「照片較新」就盲目覆寫使用者人工修正；使用者編輯過的 brand / model / attributes 需「新證據（時間戳／事件序可驗證）＋模型自報信心 >= 0.90」才允許自動套用；證據不足（< 0.90）或舊照片一律留待人工確認（`pending`）。**語意校準**：此門檻只是保守的輔助條件——程式能驗證的是來源照片存在、照片時序、欄位歷史狀態與模型回傳分數；程式**無法**獨立證明照片真的足以證實品牌或型號（自報信心在過往評測中鑑別力有限），因此不得對外宣稱 0.90 等於「照片證據充分」。
   - **自動套用可修訂**：先前由系統自動套用（`state == "auto"`）的欄位，重新分析時允許自動更新為新詮釋（可復原）。
   - **保護使用者自訂品名**：使用者手動填寫之名稱（S2 偏好）維持 `pending`，不強制覆蓋。
   - **歷史拒絕防護**：曾被使用者手動拒絕或撤回的值，嚴禁再次**自動**套用——即使有新照片存在、模型自報信心再高也一樣；允許在新證據支持下再次提出，但僅進入待確認清單（`pending`），由使用者確認。
   - **維持衝突升級**：高風險欄位（分類、狀況、備註、識別碼）維持確認式套用（`pending`）。

### 取捨
- 上下文長度增加約 1–2 KB，但仍遠在模型 token 限制內，且換得模型具備完整的「理解全貌」能力。
- 零資料庫 migration，完全相容既有資料庫。

### 驗證方式
- `tests/test_ai_analyze.py`：情境測試涵蓋歷史與識別碼完整注入、上下文語意精準區分（自動套用 vs 採納 vs Undo vs 拒絕）、初次錯誤使用者修正後追加照片利用歷史、決定性新證據更新舊判讀、弱證據不覆寫人工修正、自動套用欄位重跑舊照片自動修訂、歷史衝突與拒絕值安全防護、多識別碼跨照片保留與來源映射、超過 5 識別碼取捨；另有針對性修正測試：歷史取用順序與上限（最近紀錄優先、>500 筆窗口）、拒絕只禁止自動套用（可再次提出、永不自動覆寫）、拒絕語意文件／提示詞一致性、照片選取上限不變量（含 `max_photos=2/3` 邊界與預設 8 的識別碼保留）。

- 全套件 1107 測試無迴歸。

**狀態**：✓ Accepted（2026-10-11）

## D13. HEIC／HEIF 支援：pillow-heif 解碼、衍生預覽與證據邊界（2026-10-12）

### 背景
iPhone 預設以 HEIC 拍攝；Chrome／Edge／Firefox 無法直接顯示，Pillow 也解不開。過去 capture 在選取時明確拒收 HEIC（格式分流、不假裝支援）。需求是讓 HEIC／HEIF 完整走完「選取預覽 → 上傳 → AI 分析 → 存檔 → 詳情檢視」，同時維持既有不變量：原始檔不可轉換／覆寫／遺失；JPEG 只作預覽與 AI 的衍生資料；50 MP 像素上限與上傳大小／檔數限制不得放寬。

### 選項
1. **前端轉檔（heic2any／WASM libheif）** —— 違反零建置、零外部 CDN 原則，且手機負擔大。
2. **伺服器端 pillow-heif 解碼 ＋ 受控預覽端點** —— Windows 有預建 wheel（cp310–cp313），原始位元組不動，與現有 AI 縮圖（Pillow）同一路線。✓
3. **只靠 Safari 原生解碼** —— 對 Chrome／Edge／Firefox（多數桌面與 Android）等於不支援。

### 決定
**採用 Option 2：**
- **解碼集中**：`shop/heif.py` 統管 HEIF 偵測（ftyp brand）、零解碼尺寸（ispe metadata）、JPEG 解碼（含方向校正）與 EXIF 取出；pillow-heif 為**軟性依賴**（缺套件時 HEIC 預覽明確 400，其餘格式不受影響），但列入 `requirements.txt` 讓標準安裝直接可用。
- **三條影像用途**：(1) 選取後前端預覽 `POST /api/inbox/preview`（不落盤、不建紀錄）；(2) AI 分析 `ai_client.encode_photo` 解成 JPEG data URL；(3) 詳情／縮圖 `GET /api/photos/{id}/preview`。
- **衍生預覽邊界（補強 D6）**：預覽快取放 `files/{item}/derived/preview-v1-<sha前16>.jpg`，以原始檔 SHA-256 命名（原檔不可變 → 內容確定、可安全重生），**不登記 photos 資料列** —— 不進照片清單、證據包、列印或搜尋。瀏覽器可原生顯示的格式由 `/files` 直出原檔，不經過本端點重新編碼。尺寸統一長邊 1600px（D6 的雙尺寸設計未實作，統一尺寸即可涵蓋卡片縮圖與詳情大圖）。
- **安全邊界不變**：上傳／預覽都先以 metadata 讀寬高再解碼（JPEG／PNG 零解碼；HEIF 讀 ispe），50 MP 上限、單檔 24 MiB、每請求 20 檔、body 32 MiB 全部沿用；解碼失敗與損毀檔一律 400 並說明，不假裝成功。
- **metadata 與 EXIF**：HEIF 的尺寸與 EXIF 併入 `shop/photos` 既有讀取（`read_metadata`／`parse_metadata`／`read_captured_at`）；只有 EXIF 真解析出可靠時間才標 `captured_from="exif"`，否則沿用既有退路（mtime／檔名／留空）。TIFF 解析補強：DateTimeOriginal 允許在 IFD0（部分寫入器）或 Exif IFD。
- **選取流程**：HEIC／HEIF 不再於選取時拒收；前端保留原始 `File` 供正式上傳，向受保護 API 取得 JPEG 預覽 blob 作托盤縮圖。**預覽失敗 → 明確提示並阻止該檔進入待整理清單**；預覽未完成前停用「AI 開始整理」，不讓檔案被上傳流程漏掉。

### 取捨
- **優勢**：iPhone 照片零摩擦匯入；原檔逐位元組保存；無前端函式庫、無 CDN。
- **成本**：新增一個原生擴充依賴（pillow-heif ＋ libheif bundled，約 7 MB wheel）；HEIC 首次詳情檢視需伺服器解碼（後續走 derived 快取）。
- **風險**：解碼器漏洞面（libheif）；以「metadata 先驗尺寸 ＋ Pillow bomb 防護 ＋ 本機信任邊界」緩解；真機 iOS／Android 流程未在自動化環境驗證（需人工驗收）。

### 驗證方式
