# 3. Jobs-to-be-Done & Core Use Cases

## 3.1 主要 Job

> **當一件重要的實體物品進入或即將離開我的掌控時，我想用最少的力氣留下一份「它是什麼、它當時長什麼樣子」的可信紀錄，這樣之後無論是要找它、認它、還是證明它，我都有東西可以依靠。**

拆開來：

| 成分 | 內容 |
|---|---|
| **Trigger（何時）** | 物品**進入**（買到、收到、繼承）或**即將離開**（寄出、借出、送修、存放）我的掌控 |
| **Motivation（想要）** | 留下一份紀錄 |
| **Constraint（限制）** | 最少的力氣；物品就在手上，我沒時間坐下來填表 |
| **Outcome（為了）** | 之後**找得到**、**認得出**、**證明得了** |

## 3.2 Job Map（主要 Job 的完整步驟）

| 步驟 | 使用者要完成的事 | 目前的障礙（沒有 ItemTrace） | ItemTrace V3 的回應 |
|---|---|---|---|
| 1. 決定 | 「這件要不要留紀錄？」 | 覺得麻煩就算了 | 建檔便宜到不需要決定（P3） |
| 2. 擷取 | 拍下外觀、標籤、序號、瑕疵 | 不知道要拍哪些；拍了散在相簿 | Capture 引導角度；照片直接屬於一件物品 |
| 3. 辨識 | 知道它的品名、品牌、型號、序號 | 手抄序號、打錯 | AI 讀照片打草稿，序號附來源照片 |
| 4. 確認 | 確保紀錄是正確的 | 沒有人複核 | 逐欄確認；識別碼對照照片逐字確認；撞號提醒 |
| 5. 保存 | 確保紀錄不會丟、不會被改 | 相簿會被清、雲端會換 | 原始照片不可變、事件全紀錄、本機備份 |
| 6. 找回 | 之後找到這件東西的紀錄 | 翻相簿、搜不到序號 | 名稱／半截序號搜尋；QR 標籤直達 |
| 7. 追加 | 物品狀態改變時再留紀錄 | 不會想到；找不到原本那組照片 | 掃 QR → 新增快照（帶目的） |
| 8. 比對 | 確認「是不是同一個」「有沒有變」 | 靠記憶 | 快照並排比對；識別碼比對 |
| 9. 證明 | 把紀錄交給第三方 | 截圖一堆、對方不信 | 證據包：可讀報告 + 可驗證檔案 |

## 3.3 相關 Jobs

### 功能型

| # | Job | 對應能力 |
|---|---|---|
| J-F1 | 當我收到一件退回的物品，我想確認它是不是我寄出的那一件 | 序號搜尋 + 比對快照 |
| J-F2 | 當我要送修一件器材，我想留下送修前的狀況 | 快照（目的：送修） |
| J-F3 | 當器材失竊，我想立刻拿出序號與照片 | 搜尋 + 證據包 |
| J-F4 | 當我有一批新貨，我想一次建好全部 | 連續建檔（Next item）／桌機匯入 |

## 3.5 Jobs ItemTrace 不接

| Job | 為什麼不接 |
|---|---|
| 「幫我管理我的銷售與利潤」 | 交易系統；會讓資料模型與介面變成另一個產品 |
| 「告訴我這件東西值多少錢」 | 需要市場資料；判斷錯誤會傷害信任 |
| 「提醒我做某件事」 | 本機 Web app 無法可靠推播；以「即將到期」篩選代替 |
| 「讓我的家人也能編輯」 | 多人與權限；違反單人信任模型 |
| 「幫我自動判斷物品有沒有新損傷」 | AI 的判斷在證據情境下風險極高；提供人工並排比對代替（AI 差異提示列為 Future，且只作提示） |
